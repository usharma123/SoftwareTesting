## HIGH (1)

### Unbounded message buffering enables heap exhaustion

- **File:** `src/main/java/com/prowidesoftware/swift/io/AbstractReader.java`
- **Lines:** 154
- **Slug:** unbounded-message-memory-dos
- **Confidence:** high
- **Revalidation:** confirmed
- **Reasoning:** A bounded 32 MiB heap reproduction reliably triggered OutOfMemoryError for both RJEReader and PPCReader when processing oversized unterminated input. The readers accumulate input in unbounded StringBuilder instances before parsing, so attacker-controlled streams can exhaust application heap and cause denial of service.

AbstractReader.nextSwiftMessage() accepts the complete result of next() without enforcing a message-size limit. Its RJEReader and PPCReader implementations accumulate characters in a StringBuilder until a separator, terminator, or EOF is encountered. An attacker-controlled oversized or unterminated message can therefore exhaust the JVM heap before parsing, causing a denial of service.

Local reproduction steps:
- Compile the project classes and a local Reader that generates 100,000,000 characters without an RJE separator or PPC end marker.
- Run each reader with a bounded heap: java -Xmx32m -cp build/classes/java/main:/tmp ReaderMemoryRepro rje and repeat with ppc.
- Observe OutOfMemoryError in both cases while next() buffers the unterminated message.

Evidence:
- The bounded reproduction printed 'OUT_OF_MEMORY while reading attacker-controlled unterminated rje message' and exited 42.
- The same reproduction printed 'OUT_OF_MEMORY while reading attacker-controlled unterminated ppc message' and exited 42.
- RJEReader.next() appends every character until '$' or EOF; PPCReader.next() appends every character until END or EOF. Neither path has a length bound.
- AbstractReader.java line 154 invokes next() and passes the resulting complete string to parsing without any size validation.
- The targeted Gradle test compilation succeeded, but test execution was unavailable offline because org.jacoco.agent:0.8.13 and palantir-java-format:2.28.0 were not cached.

**Recommendation:** Introduce a configurable maximum message size and enforce it while reading in RJEReader.next() and PPCReader.next(), aborting with a documented exception once exceeded. Apply a conservative default limit and avoid constructing or parsing input larger than that limit.

## MEDIUM (5)

### BIC validation accepts non-ASCII Unicode letters and digits

- **File:** `src/main/java/com/prowidesoftware/swift/constraints/BicConstraint.java`
- **Lines:** 40, 166, 175
- **Slug:** unicode-bic-validation-bypass
- **Confidence:** high
- **Revalidation:** confirmed
- **Reasoning:** The code deterministically accepts non-ASCII uppercase letters and Unicode digits through Character.isUpperCase/isDigit, and BicValidator propagates BIC.validate() success. The regression test compiled; execution was blocked only by unrelated offline JaCoCo/Spotless dependencies. This standards-validation bypass can cause interoperability and allowlist inconsistencies.

BicValidator accepts malformed identifiers outside the ISO 9362 BIC alphabet. BIC.validate() uses Character.isUpperCase and Character.isDigit, which recognize Unicode characters such as fullwidth Latin letters and Arabic-Indic digits. Consequently, visually deceptive or downstream-incompatible identifiers can bypass the validation constraint, creating inconsistent validation, normalization, routing, or allowlist behavior between systems expecting ASCII BICs.

Local reproduction steps:
- Call `new BicValidator().isValid("\uFF21\uFF22\uFF23\uFF24US22", null)`; it returns true although the institution contains fullwidth Unicode letters.
- Call `new BicValidator().isValid("BANKUS\u0662\u0663", null)` or use Arabic-Indic digits in the branch; validation returns true because Character.isDigit accepts them.
- Compare with an ASCII-only BIC consumer or the documented BIC alphabet, which rejects these identifiers.

Evidence:
- BicValidator.java:40 treats any `new BIC(bic).validate()` result of OK as valid.
- BIC.java:166 accepts every character for which `Character.isUpperCase(char)` is true, rather than restricting the institution to ASCII A-Z.
- BIC.java:175 accepts every Unicode digit recognized by `Character.isDigit(char)`, rather than restricting location and branch digits to ASCII 0-9.
- The reproduction test compiled successfully; execution was blocked by unrelated offline build dependencies for JaCoCo and Spotless.

**Recommendation:** Validate institution characters explicitly as ASCII A-Z and location/branch characters explicitly as ASCII A-Z or 0-9. For example, use direct character ranges or full-string patterns equivalent to `[A-Z]{4}[A-Z]{2}[A-Z0-9]{2}([A-Z0-9]{3})?`, with separately defined handling for supported 12-character logical-terminal addresses.

### Shared enum state leaks BIC values across validations

- **File:** `src/main/java/com/prowidesoftware/swift/constraints/BicValidator.java`
- **Lines:** 43, 54, 56, 57, 66, 67
- **Slug:** bic-validation-cross-request-data-leak
- **Confidence:** high
- **Revalidation:** confirmed
- **Reasoning:** The standalone reproduction confirms that validations return the same mutable enum singleton and that a later validation changes an earlier result's message. The unsynchronized validate-to-message interval makes cross-request message substitution possible, causing integrity errors and limited disclosure of user-supplied BIC fragments.

BicValidationResult enum constants are JVM-wide singletons but contain a mutable `found` field. Each BIC validation overwrites that shared field via setFound(), while message() reads it later without synchronization. Concurrent validations can therefore return another request's malformed BIC fragment, causing cross-request information disclosure and incorrect validation messages. The standalone reproduction also proves that previously returned results mutate even during sequential validation.

Local reproduction steps:
- Validate `aaaaUS12`, retain the returned BicValidationResult, and call message().
- Validate `bbbbUS12`, which produces the same enum constant.
- Call message() again on the first result and observe that its reported value changed from `aaaa` to `bbbb`.
- Run validations concurrently around BIC.validate() and BicValidator.isValid() to trigger cross-request message substitution.

Evidence:
- BicValidationResult.java declares mutable singleton state at line 43 (`private String found`) and overwrites it at lines 66-68.
- message() reads the shared field at lines 54-57; BicValidator.java lines 40-45 obtains the result and renders the message in separate operations, permitting an interleaving validation.
- Standalone reproduction exited successfully with `sameSingleton=true`; its output changed from `before=... aaaa was found` to `after=... bbbb was found`.
- The Gradle test could not execute because offline JaCoCo and Spotless artifacts were unavailable, but compilation succeeded and the standalone Java reproduction ran against the compiled project classes.

**Recommendation:** Make validation results immutable and per-validation. Replace the mutable enum field/setFound pattern with a result object containing a final result code and final found value, and render messages from that instance. Do not synchronize or use ThreadLocal as a substitute for eliminating shared mutable enum state.

### Unicode uppercase characters accepted in user-assigned country codes

- **File:** `src/main/java/com/prowidesoftware/swift/constraints/CountryConstraint.java`
- **Lines:** 100
- **Slug:** unicode-country-code-validation-bypass
- **Confidence:** high
- **Revalidation:** confirmed
- **Reasoning:** The inspected code directly confirms the bypass: two-character inputs beginning with ASCII X are accepted when Character.isUpperCase recognizes the second UTF-16 character as Unicode uppercase, so values such as XÉ pass despite not belonging to the ASCII XA-XZ user-assigned range. This is a real validation and data-integrity issue worth retaining, though its impact remains bounded.

The user-assigned country-code check requires an ASCII 'X' but validates the second character with Character.isUpperCase. That API accepts many non-ASCII Unicode uppercase characters, so two-character values such as "XÉ" or "XΑ" are accepted despite not being valid ISO 3166 user-assigned codes. Callers including CountryValidator, BIC, and IBAN validation can therefore accept malformed identifiers.

Local reproduction steps:
- Call `IsoUtils.getInstance().isValidISOCountry("XÉ")`.
- Observe that the two-character input reaches `isUserAssignedCountryCode`, where `Character.isUpperCase('É')` returns true, causing validation to succeed.
- Repeat through `CountryValidator.isValid("XÉ", context)` and observe the malformed country code is accepted.

Evidence:
- IsoUtils.java lines 92-95 accept any two-character value that is either in the ISO set or passes `isUserAssignedCountryCode`.
- IsoUtils.java line 100 implements the user-assigned check as `code.charAt(0) == 'X' && Character.isUpperCase(code.charAt(1))`, which is Unicode-aware rather than ASCII-restricted.
- The existing tests cover only ASCII XA-XZ and do not test Unicode uppercase characters.

**Recommendation:** Restrict both characters to ASCII explicitly, for example `code.length() == 2 && code.charAt(0) == 'X' && code.charAt(1) >= 'A' && code.charAt(1) <= 'Z'`. Add regression tests for non-ASCII uppercase characters.

### Shared mutable IBAN validation results leak data across requests

- **File:** `src/main/java/com/prowidesoftware/swift/constraints/IbanConstraint.java`
- **Lines:** 60, 69, 71, 72, 81, 82, 89, 90, 97, 98, 105, 106, 113, 114, 120, 121
- **Slug:** shared-mutable-validation-result
- **Confidence:** high
- **Revalidation:** confirmed
- **Reasoning:** Enum constants are process-wide singletons, yet each contains a mutable HashMap populated with input-derived values on every validation. Reusing the same error constant deterministically overwrites retained results, while concurrent validation can race and expose or misattribute another request's data. The public vars() accessor further exposes the shared state directly.

IbanValidationResult is an enum, so each result is a process-wide singleton, but every singleton contains a mutable HashMap of message variables. Each validation overwrites this shared state with input-derived country codes, BBANs, characters, and check digits. A retained result can therefore change after another validation, and concurrent requests can receive messages containing another request's data. Concurrent HashMap reads and writes are also unsafe. The public vars() method exposes the shared map directly. IbanValidator makes this reachable in server applications by rendering result.message() as the Bean Validation violation template.

Local reproduction steps:
- Call IBAN.validate("ZZ12A") and retain the returned INVALID_COUNTRY_CODE result; its message initially contains ZZ.
- Call IBAN.validate("US12A"); it returns the exact same enum instance and overwrites its shared found variable.
- Read message() from the first retained result again; it now contains US rather than ZZ. In concurrent Bean Validation requests, the same race can disclose or misattribute another request's input.

Evidence:
- IbanValidationResult.java:30 declares the result type as an enum, while line 60 creates a mutable HashMap on each globally shared enum constant.
- IbanValidationResult.java:69-73 renders messages by iterating the shared vars map; setters at lines 81-114 overwrite that map with validation-specific values.
- IbanValidationResult.java:120-121 returns the mutable shared map directly.
- IbanValidationUtils.java:55-62 demonstrates that INVALID_COUNTRY_CODE.setFound(countryCode) is invoked for each invalid input; numerous other paths similarly store input-derived BBAN and check-digit data.
- IbanValidator.java:40-45 validates caller input and places result.message() into the constraint violation, providing a common cross-request message sink.
- The regression test compiled successfully, but Gradle could not execute tests offline because the JaCoCo agent and Palantir formatter artifacts were not cached; the observed singleton identity and overwrite follow directly from Java enum and HashMap semantics.

**Recommendation:** Make each validation outcome immutable and request-local. Keep the enum only as a stateless error code/template and return a new result object containing an immutable copy of that validation's parameters. Remove the enum setters, never expose a mutable parameter map, and render the message from the per-call result. Prefer a fixed Bean Validation template with safely supplied message parameters rather than passing dynamically rendered input as the template.

### Mutable enum state leaks IBAN fragments across validations

- **File:** `src/main/java/com/prowidesoftware/swift/constraints/IbanValidator.java`
- **Lines:** 45, 72, 81, 134
- **Slug:** shared-iban-validation-state
- **Confidence:** high
- **Revalidation:** confirmed
- **Reasoning:** The enum constants are shared process-wide while setFound() stores per-validation IBAN data in mutable state later consumed by message(). Two validations producing the same result constant can overwrite one another, enabling incorrect messages and cross-request IBAN-fragment disclosure. The supplied test execution was blocked by missing offline build/runtime dependencies, but compilation and source-level singleton aliasing establish a deterministic local reproduction path.

IbanValidationResult enum constants are process-wide singletons but store request-specific message variables in a mutable HashMap. Validation writes attacker-controlled IBAN fragments through setFound(), while message() reads the same shared state and IbanValidator exposes the rendered text as a constraint violation. Concurrent or delayed rendering can therefore substitute data from another validation, causing cross-request disclosure of IBAN/account fragments and incorrect validation messages.

Local reproduction steps:
- Validate an invalid IBAN that produces BBAN_INVALID_LENGTH and retain the returned result before calling message().
- Validate another invalid IBAN producing the same enum constant but containing a different BBAN fragment.
- Call message() on the first retained result; because both references are the same enum singleton, it renders the second validation's fragment. A concurrent test can place a barrier between validate() and message() to reproduce the cross-request race.

Evidence:
- IbanValidationResult.message() reads mutable per-message variables from the enum singleton at line 72, and setFound() overwrites them at line 81.
- IbanValidationUtils writes the submitted BBAN into BBAN_INVALID_LENGTH at line 134.
- IbanValidator passes result.message() to buildConstraintViolationWithTemplate() at line 45, exposing the raced value to callers.
- The attempted JUnit build reached compileTestJava successfully but execution was blocked by unavailable offline JaCoCo and Spotless artifacts; the independent probe was blocked only by a missing runtime commons-lang3 class. These environmental failures do not alter the source-level singleton aliasing.

**Recommendation:** Make validation details immutable and per invocation. Return a new result object containing the result code and an immutable copy of its message parameters; keep enum constants stateless. Render from that object without shared mutation, and return an unmodifiable parameters map.

## BUG (1)

### Block 2 output direction compares digit zero instead of letter O

- **File:** `src/main/java/com/prowidesoftware/swift/io/parser/SwiftParserConfiguration.java`
- **Lines:** 206
- **Slug:** block2-direction-confusion
- **Confidence:** high
- **Revalidation:** confirmed
- **Reasoning:** The source and direct execution confirm the O/0 typo and inconsistent classification. However, valid full output headers are generally still classified as output by the length heuristic, so the claimed authorization/routing impact and HIGH severity are speculative; this is primarily a correctness bug.

SwiftParser.parseBlock2 compares the extracted direction against '0' rather than the valid SWIFT output marker 'O'. Consequently, malformed digit-zero headers are accepted as output blocks, while short letter-O values fall through to the length heuristic and can be classified as input. Applications that use this public helper and trust the parsed direction for authorization, routing, or validation can process attacker-controlled messages in the wrong direction context.

Local reproduction steps:
- Compile the project classes and obtain the main runtime classpath.
- Call SwiftParser.parseBlock2 for values I103BANKDEFFXXXXU3003, O, and 0, then print each resulting class and block type.
- Observe that O becomes SwiftBlock2Input with a null type, while invalid 0 becomes SwiftBlock2Output with type O.

Evidence:
- Source line 206 uses Character.valueOf('0').equals(block2Type), whereas the normal parser path at line 475 correctly compares Character.valueOf('O').
- Direct reproduction output: O => SwiftBlock2Input, type=null; 0 => SwiftBlock2Output, type=O.
- The focused Gradle test could not execute because offline dependencies for JaCoCo and Palantir Java Format were unavailable, but the already-compiled production classes reproduced the defect directly.

**Recommendation:** Change the comparison at line 206 from Character.valueOf('0') to Character.valueOf('O'). Reject unknown direction markers rather than assigning direction by length, or clearly expose the parse error. Add regression tests asserting that O creates SwiftBlock2Output and 0 is rejected or remains invalid.
